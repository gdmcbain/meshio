# Cecoio Testing Principles

## Purpose

Cecoio is an interchange library. Its primary responsibility is not merely to preserve data through its own code, but to **read and write external file formats correctly and interoperably**.

The test suite should therefore distinguish carefully between:

1. correctness of the neutral `Ceco` representation;
2. correctness of a format reader;
3. correctness of a format writer;
4. preservation of information through a Cecoio round trip;
5. interoperability with independent implementations of a format.

These are related, but they are not equivalent.

## 1. A reader and writer must not be each other's primary oracle

A test of the form

```text
Ceco
  ↓
our writer
  ↓
file
  ↓
our reader
  ↓
Ceco
```

followed by a comparison of the two Ceco objects is useful, but **does not establish that either the reader or writer implements the external format correctly**.

The reader and writer may share the same misunderstanding of the format. Their errors may cancel:

\[
R(W(c)) = c
\]

even though `W(c)` is not a valid or semantically correct representation according to the external format.

As Geordie McBain put it during earlier meshio development:

> I feel a bit uncomfortable that the test of my `read` is to be my `write`, as if I were correcting my own Russian homework rather than getting a native speaker to do it.

**Principle:** a format implementation should, wherever practicable, be tested against an oracle independent of Cecoio.

## 2. Reader tests should start from independently produced files

The preferred reader test is:

```text
authoritative fixture
        ↓
 Cecoio reader
        ↓
      Ceco
        ↓
expected semantics
```

Fixtures should preferably be:

- produced by an authoritative or widely accepted implementation of the format;
- taken from an official format test suite or examples;
- derived directly from the format specification;
- or small enough to be independently inspected and verified by a human.

Cecoio's writer should not generate the primary fixtures used to establish correctness of the corresponding reader.

Each fixture should test a **specific format feature** where practical. For example:

```text
minimal triangle
mixed cell types
higher-order elements
physical/groups/sets information
point fields
cell fields
binary encoding
endianness
time-dependent fields
unusual but legal constructs
```

Prefer small, intelligible fixtures over large opaque "realistic" files.

## 3. Writer tests should use an independent consumer

The preferred writer test reverses the direction:

```text
known Ceco
    ↓
Cecoio writer
    ↓
 external file
    ↓
authoritative reader
    ↓
expected semantics
```

For example, a Gmsh writer should ideally be tested by asking Gmsh to read its output, rather than by asking Cecoio's Gmsh reader to read it.

Likewise, where practical:

- VTK-family output should be checked with VTK;
- Gmsh output with Gmsh;
- MED output with an independent MED implementation;
- Exodus output with its established ecosystem;
- and so forth.

This is **interoperability testing**, which is ultimately the reason Cecoio exists.

The relevant question is not

> Can Cecoio understand the file Cecoio wrote?

but

> Can another correct implementation understand the file Cecoio wrote, with the intended meaning?

## 4. Specifications and reviewed golden files are also independent oracles

An external executable is not always necessary or practical.

For sufficiently simple formats and examples, compare writer output against a small, reviewed **golden file** whose correctness is established independently from the writer under test.

For textual formats especially, a useful test may be:

```text
known Ceco
    ↓
 writer
    ↓
actual text
    ↕
reviewed expected text
```

Golden files should not be casually regenerated by the implementation being tested and then accepted merely to make tests pass.

A changed golden file is a **reviewable statement that our understanding of the external format has changed**.

## 5. Round-trip tests remain useful, but call them what they are

Round-trip tests should not be discarded.

They test an important property:

> Does Cecoio preserve the intended information when it writes and rereads a representation?

For appropriate Ceco `c`,

\[
R(W(c)) \simeq c
\]

is a desirable invariant.

Round-trip tests are particularly useful for cheaply covering combinations of:

- cell types;
- numeric types;
- field shapes;
- optional metadata;
- encodings;
- compression choices.

But they are **regression and information-preservation tests, not independent format-conformance tests**.

A green round-trip test must never be taken by itself as evidence that the generated file conforms to its specification.

## 6. `Ceco` itself should be tested independently of file formats

The neutral representation deserves ordinary focused unit tests.

These should cover matters such as:

- construction;
- normalization of inputs;
- indexing and access;
- `CellBlock` behaviour where retained;
- copying and aliasing semantics;
- equality/comparison semantics where defined;
- delegation and structural compatibility;
- future geometry/cell relationships as they are introduced.

A bug in `Ceco` should not require debugging through a file reader or writer to expose it.

Likewise, format-specific conventions should not leak into core `Ceco` tests.

## 7. Test semantics, not incidental representation

Interchange formats frequently admit multiple equivalent encodings.

Tests should therefore normally compare the **meaning** of an object rather than requiring byte-for-byte equality.

For example, two files may differ harmlessly in:

- whitespace;
- ordering where the format declares ordering insignificant;
- floating-point formatting;
- optional metadata;
- compression;
- generated identifiers.

Byte-for-byte tests are entirely appropriate when the bytes themselves are significant, but should not substitute for semantic testing.

## 8. Tiny fixtures should be comprehensible

A good test fixture should make failures diagnosable.

Prefer a fixture containing two triangles and one physical group over a 45 MB industrial mesh if both exercise the same parser feature.

Ideally, a developer investigating a failed test should be able to inspect:

```text
fixture
expected Ceco properties
test assertion
```

and understand the discrepancy without reverse-engineering an unrelated simulation.

Large real-world meshes are valuable as an additional integration corpus, not as a replacement for focused tests.

## 9. Record fixture provenance

Independently generated fixtures should say where they came from.

For example:

```text
tests/data/gmsh/4.1/
    quadratic-line.msh
    quadratic-line.md
```

with the accompanying documentation recording information such as:

```text
Producer: Gmsh
Producer version: ...
Format: MSH 4.1 ASCII
Purpose: quadratic line-element reader fixture
Generation source/command: ...
Expected entities: ...
```

Where reproducible generation is practical, retain the source script or commands as well.

The binary fixture is then **evidence**, rather than an unexplained blob that happened to make a test pass in 2027.

## 10. Separate ordinary tests from external conformance tests

Developers should not need to install every supported mesh ecosystem to run the normal unit suite.

A useful division is:

```text
tests/
    unit/
    readers/
    writers/
    roundtrip/
    conformance/
    data/
```

The ordinary suite can use checked-in authoritative fixtures and reviewed goldens.

A separate conformance suite can depend upon external reference implementations:

```text
conformance:
    Gmsh
    VTK
    MED
    Exodus
    ...
```

These tests can run in suitable CI environments, scheduled workflows, release validation, or format-specific jobs.

Thus we obtain independent testing without making `pytest` require half the scientific-computing ecosystem.

## 11. Establish the baseline before attributing failures to a change

When modifying legacy code, first run the test suite against the exact unmodified baseline.

Record:

```text
baseline commit
environment
passed
failed
skipped
xfailed
```

Then test the proposed change in the same environment.

A failing test on a feature branch is a regression only if it did not fail on the baseline.

Do not modify unrelated old tests merely to make a new branch green.

For the current Ceco spike in particular:

> **First classify failures as baseline failures or spike regressions. Fix only the latter as part of the spike unless a baseline repair is deliberately taken on as separate work.**

## 12. Do not weaken a test to accommodate an implementation

When a legitimate test exposes a bug, fix the implementation.

If a test itself is wrong, document why before changing its expectation.

In particular, avoid:

- regenerating goldens from the failing implementation;
- replacing precise assertions with weaker assertions simply to obtain green CI;
- silently dropping unsupported information during comparisons;
- adding broad `xfail` or skip markers without documenting the underlying incompatibility.

A red test is information.

## 13. Readers and writers should ultimately be testable independently

Architecturally, strive for:

```text
external format
      ↓
    Reader
      ↓
     Ceco
```

and independently:

```text
     Ceco
      ↓
    Writer
      ↓
external format
```

This makes `Ceco` a genuine semantic boundary.

The reader answers:

> What does this external representation mean in Ceco?

The writer answers:

> How can this Ceco be represented in the external format?

Neither question intrinsically requires running the implementation of the other direction.

## 14. Test loss and unsupported features explicitly

Because Ceco may eventually be more expressive than individual external formats, writer testing must eventually cover not just successful output but **honest failure**.

For a feature unsupported by a target format, expected behaviour should be explicitly tested as one of:

```text
represent faithfully
drop only under an explicit lossy policy
raise a clear unsupported-representation error
```

Silent accidental information loss is a serialization bug.

## 15. Test the boundaries where formats disagree

The most valuable interchange tests often concern the places where neutral abstractions do **not** map perfectly onto external formats.

As Ceco evolves, prioritize tests around questions such as:

- differing cell-node order conventions;
- zero- versus one-based numbering;
- higher-order elements;
- sets/groups/physical entities;
- mixed-dimensional structures;
- nonconforming structures;
- transient fields;
- distinctions between nodal, cellular and other field associations;
- geometry that one format represents more richly than another.

These are precisely the areas where a neutral interchange library earns its keep.

## Testing hierarchy

No one testing technique establishes everything. Think in layers:

```text
                  specification
                       │
        ┌──────────────┴──────────────┐
        │                             │
 authoritative                   reviewed
 implementation                 golden data
        │                             │
        └──────────────┬──────────────┘
                       │
               conformance tests
                       │
                     Ceco
                 ┌─────┴─────┐
                 │           │
            reader tests  writer tests
                 │           │
                 └─────┬─────┘
                       │
                round-trip tests
                       │
                regression coverage
```

Each layer answers a different question.

## The short version

If this needs boiling down to five rules for `CONTRIBUTING.md`:

1. **Never use our reader as the primary oracle for our writer, or vice versa.**
2. **Test readers against independently produced, authoritative fixtures.**
3. **Test writers with independent consumers, specifications, or reviewed golden files.**
4. **Keep round trips, but treat them as information-preservation tests, not proof of format conformance.**
5. **Test `Ceco` as a neutral representation independently of individual formats.**

The Russian-homework aphorism captures the central idea: Cecoio should not mark its own homework when an independent oracle is available.
